# ADR-0001. 아키텍처 결정을 ADR로 기록한다

- 상태: Accepted
- 날짜: 2026-09-03

## 배경

CareerOS에는 구현 중에 반드시 다시 흔들릴 결정들이 있다.

- Fit Score를 왜 LLM에게 계산시키지 않는가
- 왜 Career Evidence 밖의 사실을 쓰지 않는가
- 왜 생성 문장마다 Evidence Reference를 요구하는가

이 결정들은 대부분 **더 편한 대안을 거절한 결과**다.
LLM에게 "82점"을 물어보는 게 가중치 계산기를 만드는 것보다 빠르고,
근거 없이 문장을 생성하는 게 "근거 부족"을 표시하는 것보다 결과물이 그럴듯하다.

그래서 시간이 지나면, 혹은 다른 사람(또는 다른 AI 에이전트)이 코드를 만지면
"이거 그냥 LLM한테 시키면 되는데 왜 이렇게 복잡하지?"라는 이유로 되돌아간다.
결정의 **근거**가 남아 있지 않으면 막을 방법이 없다.

## 결정

되돌리기 어렵거나 되돌리면 제품 정체성이 바뀌는 결정을 `docs/adr/`에 기록한다.

형식:

```text
docs/adr/NNNN-kebab-case-title.md

- 상태: Proposed | Accepted | Superseded by ADR-NNNN
- 날짜
## 배경    무엇 때문에 결정이 필요했는가
## 결정    무엇을 하기로 했는가
## 이유    왜 대안 대신 이것인가
## 결과    이 결정이 코드에 무엇을 강제하는가
```

기록 대상:

- 도메인의 사실 기준을 정하는 결정
- AI 출력의 신뢰성에 관한 제약
- 되돌리려면 데이터 마이그레이션이 필요한 결정

기록 대상이 아닌 것:

- 라이브러리 선택 같은 교체 가능한 결정 (`docs/03-architecture/tech-stack.md`로 충분)
- 코딩 스타일

## 이유

문서는 "무엇을 하는가"를 남기지만 ADR은 **"무엇을 하지 않기로 했는가"** 를 남긴다.
CareerOS에서 중요한 제약은 대부분 후자다.

## 결과

- 새 ADR은 번호를 이어서 붙인다. 기존 ADR을 수정하지 않고, 뒤집을 때는 새 ADR을 쓰고 이전 것을 `Superseded`로 표시한다.
- 코드 리뷰에서 ADR에 어긋나는 구현이 보이면, 구현을 고치거나 ADR을 새로 쓴다. 조용히 넘어가지 않는다.
